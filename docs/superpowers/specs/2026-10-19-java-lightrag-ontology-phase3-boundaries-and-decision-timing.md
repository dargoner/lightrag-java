# lightrag-java 本体 Phase 3：边界与决策时点

- 状态：草案，供 Phase 3 立项使用，**尚未批准实施**。
- 日期：2026-10-19
- 关系：Phase 2（2A 属性物化与校验、2B 确定性 bootstrap、2C RDF 互操作）已完成并通过评审。
  本文件只界定 Phase 3（ontology evolution / backfill）的边界、待决策项与拍板时点，
  不包含实施方案。

## 1. 结论

Phase 2 计划附录 A 的四项开放项均**推迟到 Phase 3 立项时定案**，不构成 0.33.0 的发布门禁。
现在只澄清 Phase 2 的现有行为，不提前冻结 Phase 3 设计，也不对外承诺演化、逐属性追溯或
全量迁移能力。

## 2. 不可协商的不变量

- 本体版本不可变、追加式、**永久保留**；不设 TTL、定时清理、后台 prune 或删除 API，
  也不设"误创建/合规"删除例外。
- 回填操作本身不产生版本，只记录 `operationId`；`current_version` 与 KB `pinned_version`
  仍归宿主。
- schema 变更与数据对齐按"先数据、后 schema 提交"的顺序执行；失败时读者仍看到旧版本，
  不暴露"已声明但数据未对齐"的中间态。
- 关系属性必须纳入 evolution，不能沿用 GraphRAG-SDK 的 `NotImplementedError`。

## 3. Phase 2 当前事实（作为 Phase 3 的起点）

- **投影发生在合并存量之后**：普通写入会裁剪被本次写入触及的记录中"最终类型未声明"的键；
  这不是"删除声明即全量迁移"，未被本次写入触及的记录保持原样。
- 缺失键读取等价于 `null`；写入侧省略 null，记录构造不接受 null 值。
- 属性逐键 last-write-wins，没有逐属性的版本或 operation 来源。
- chunk 已有 `metadata` 与 `contentHash`，但没有 evolution 操作标记。
- 六个后端均支持 attributes 读写；`GraphStore` 只有 `allEntities/allRelations`，
  没有按类型分页、游标或迁移一致性契约。
- 已被裁剪的属性值和未记录的历史来源无法追回；旧数据未来只能标记为"来源未知"。

## 4. 决策表

| 开放项 | 裁定 | 推荐方向 | 最晚定案时点 |
|---|---|---|---|
| A.4-2 投影语义 | 推迟到三期立项时 | 三期选 A；二期保持现状 | 演化写入获准前 |
| A.4-3 chunk 操作标记 | 推迟到三期立项时 | 优先宿主操作表，SDK 约定执行与确认语义 | 首次持久化回填进度前 |
| A.4-4 属性来源 | 推迟到三期立项时 | 独立来源记录，不嵌入业务属性袋 | 首次要求可追溯的写入前 |
| A.4-5 扫描/迁移原语 | 推迟到三期立项时 | 六后端通用承诺由 SDK 提供统一契约，宿主负责编排与版本提交 | 三期范围与架构批准时 |

### A.4-2 投影语义

- **推荐方向**：Phase 3 选 A——投影只裁剪"本次抽取新带入的键"，存量未声明键保留到显式迁移；
  Phase 2 继续保持现有投影行为。
- **拍板前置**：并发写入策略、"数据领先 schema"窗口的恢复口径、以及最终投影如何区分
  存量值与本次新值。选 A 不等于取消最终投影，本次抽取中来自非最终类型的未声明键仍须裁剪。
- **风险**：Phase 2 已裁剪的值无法通过切换 A 恢复；A 是行为兼容性变化，需要明确启用与升级边界，
  但不需要改变属性袋或快照格式。

### A.4-3 逐 chunk 操作标记

- **推荐方向**：宿主操作表优先，避免为不断增长的操作历史扩展公共 chunk record；
  SDK 负责约定执行、确认与重试语义。
- **拍板前置**：执行器、事务边界、跨进程协调、备份恢复方案；标记必须绑定 chunk 内容身份，
  并明确"数据写成功、标记未成功"时的幂等重试。
- **风险**：标记选错可能误跳过已变更 chunk 或重复调用 LLM、重复合并；宿主旁路表若未随图
  一起恢复，会出现"标记已完成、数据已回退"的不一致。

### A.4-4 逐属性来源/版本可追溯

- **推荐方向**：独立来源记录，不占用受本体投影和容量上限约束的业务属性键。
- **拍板前置**：先确定追踪"当前值最后一次写入"还是"全部候选证据与覆盖历史"，再定物理方案；
  同时明确普通抽取、人工编辑、覆盖/删除如何更新来源，以及来源数据的恢复范围。
- **风险**：Phase 2 未记录的历史来源不能可靠补造。若要求从 Phase 2 第一笔写入开始完整追溯，
  需要重新立项；当前边界不包含该要求。

### A.4-5 六后端扫描/迁移原语

- **推荐方向**：若 Phase 3 承诺六后端通用能力，SDK 提供统一的扫描/迁移契约，
  宿主负责预算、调度、停写窗口与版本提交。
- **拍板前置**：确定支持后端、规模、一致性目标与停写窗口；无需现在决定分页 API 或各后端
  优化方式。
- **风险**：全量枚举可能产生内存与运行时间问题；绕过 SDK 直接改库易造成图、chunk 快照与恢复
  行为不一致；只迁移当前图而遗漏 chunk 快照时，后续重物化可能重新带回旧键。

## 5. 与 0.33.0 发布的关系

- 本文件不引入任何 Phase 3 代码、表结构或 API。
- 0.33.0 只需如实披露 Phase 2 的投影行为：普通写入可能裁剪被触及记录的存量未声明键，
  但没有立即全图迁移保证。
- 0.33.0 不应对外宣称支持逐属性版本追溯、ontology evolution 或 backfill。

## 6. Phase 3 启动前置

1. 在各自"最晚定案时点"前完成四项决策并留档。
2. 用 50 份领域文档做一次 `dry_run` spike，量化 `chunks_in_scope`、LLM 成本、失败与续跑代价，
   并覆盖关系属性。
3. spike 通过后再写完整实施计划；本文档不包含表结构、record 字段、具体 API、六后端迁移脚本
   和完整执行计划。
